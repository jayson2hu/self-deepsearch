## 1. 结论

1. 广告放在用户看到主要内容之后，不能占据查询的首要位置。保留“有有效广告时匿名和登录用户都可见，无广告不占位”；新增页面级投放管理。
2. 后台已有权限与账号状态管理，但缺少可靠总量、筛选与分页。当前测试库只有 3 条账号记录，普通用户账号为 0，不能作为生产注册量。
3. SEO 已有技术基础和逐实体分类入口，下一步补集中诊断、问题处理和效果监控，不另建一套与发布流程脱节的 SEO 配置。

## 2. 广告放在哪里

### 当前实现与问题

- 首页主搜索之后已有内容区，但正文后连续放置横幅和信息流两个槽位，同时存在双侧栏与全局页脚槽位。全部配置后可能堆叠过多广告。
- 搜索与作品详情在核心结果/资料之前存在顶部横幅；许多目录页面也使用顶部横幅与双侧栏。
- 全局页脚包含广告槽，登录、注册、个人中心等页面也共享该页脚；配置页脚广告后会扩散到这些页面。
- 当前配置以 `placement:label` 匹配。相同标签跨页面复用，不能独立表达“只在首页投放、详情停投”。
- 已有有效期、素材与目标地址校验、HTTPS 主机白名单、广告标识、付费链接标记，以及无有效配置时不渲染。没有广告后台、投放报表或曝光/点击统计。

依据：[首页](../../apps/display-web/app/page.tsx)、[搜索](../../apps/display-web/app/search/page.tsx)、[作品详情](../../apps/display-web/app/works/[slug]/page.tsx)、[全局页脚](../../apps/display-web/components/site-footer.tsx)、[配置策略](../../apps/display-web/lib/ad-policy.ts)、[广告组件](../../apps/display-web/components/ad-slot.tsx)。

### 建议布局

| 页面 | 桌面端 | 移动端 | 不放的位置 |
| --- | --- | --- | --- |
| 首页 | 最新内容区之后 1 个横幅；足够宽时可加右侧栏 | 最新内容区之后 1 个内容间广告 | 搜索框之前、紧贴输入框、连续堆叠两个广告 |
| 作品/人物/厂牌详情 | 核心资料之后、关联内容之前；足够宽时可加右侧栏 | 核心资料之后 1 个 | 标题与核心资料之间、遮挡封面/字段 |
| 搜索结果 | 首期无广告；后续仅在结果充足时考虑第 6～8 条自然结果之后 | 首期无广告 | 首个结果、空结果、错误状态 |
| 最新/热门/目录列表 | 内容充足时第 8～12 条后或分区之间 1 个 | 同位置最多 1 个 | 空列表、很短的列表、与页脚广告连排 |
| 登录/注册/找回密码/邀请/个人中心/隐私/权利申诉/后台 | 不投放 | 不投放 | 整页 |

首期每页桌面端最多 2 个、移动端最多 1 个；不使用双侧栏夹住正文、不使用悬浮底部广告或遮屏弹窗。该数量与插入位置是本产品的初始建议，不是 Google 的强制标准。页脚不再承担全站默认投放，由具体页面预算决定是否使用。

Google 建议避免妨碍内容访问的插页式广告；付费链接应使用 `rel="sponsored"`，现有组件应保留此标记。[干扰性广告说明](https://developers.google.cn/search/docs/appearance/avoid-intrusive-interstitials?hl=zh-cn)、[付费链接标记](https://developers.google.cn/search/docs/crawling-indexing/qualify-outbound-links?hl=zh-cn)。

### 建议广告后台 `/ads`（新增）

- 使用稳定槽位编码，例如 `home.after_latest`、`work.after_summary`、`list.after_items`、`desktop.right`；显示名称不参与身份判断。
- 字段：广告名称、广告主、素材、替代文本、目标 URL、页面类型、设备范围、槽位、优先级、生效/结束时间、启停状态；明确显示 Asia/Shanghai 与实际存储时区。
- 状态：草稿、计划中、投放中、暂停、过期、校验失败；预览不得进入正常用户页面。
- 同槽冲突采用明确的优先级和稳定排序；首期不引入竞价或随机轮播。保留 HTTPS/主机白名单，不允许粘贴任意第三方脚本。
- owner 发布与紧急停投；admin 可编辑草稿。所有变更留审计。扩大权限需单独确认。
- 发布/暂停触发相关缓存失效；缓存有效期不得跨越生效/到期边界，避免过期广告继续展示。
- 素材加载失败不留下大块空白；确定展示的素材声明尺寸，验证加载和失败转换不会造成明显布局跳动。
- 首期可只管理投放，不伪造转化率。增加统计前先区分返回广告、实际可见曝光与点击；不传搜索词、账号标识，不默认引入匿名跨站追踪。

复核 SQL（只读，不输出邮箱）：

```sql
SELECT now() AS observed_at,
       count(*) AS account_rows,
       count(*) FILTER (WHERE account_status = 'active') AS active_accounts,
       count(*) FILTER (WHERE account_status = 'closed') AS closed_accounts,
       count(*) FILTER (WHERE role = 'user') AS ordinary_accounts,
       count(*) FILTER (WHERE role = 'user' AND account_status = 'active') AS active_ordinary_accounts,
       count(*) FILTER (WHERE role = 'user' AND email_verified_at IS NOT NULL) AS verified_ordinary_accounts
FROM platform.users;
```

### 建议补齐的能力与统计口径

1. 顶部显示当前普通账号、启用普通账号、已验证普通账号、管理账号、已关闭账号，并标注环境与统计时间。
2. 列表支持邮箱/用户 ID 查询、角色/状态/创建时间筛选、稳定游标分页；增加验证状态和最近登录时间。全库总量与筛选总量分别命名。

4. 要做“累计完成注册、今日新增、近 7 日新增”，需明确来源 `public_signup/invitation/bootstrap/fixture/unknown`、测试标记及首次完成验证注册的不可变时间。当前角色和 `created_at` 无法准确区分公开注册、邀请及后续提权。
5. 旧数据来源未知就保留 unknown，不猜测回填；生产统计不依赖邮箱后缀猜测测试账号。按 Asia/Shanghai 划分每日边界，说明是否包含已关闭账号。

技术建议：新增 owner/admin 专用聚合接口，列表改为真实分页；计数走数据库聚合，不把所有用户拉到浏览器计数。聚合返回时间、环境、口径版本；同一响应的分类计数在同一快照计算。同步 OpenAPI，权限由 API 强制校验，不只隐藏按钮。

## 4. SEO 与优化项如何管理

### 现有能力

已有 canonical、robots、sitemap、结构化数据和发布门禁；实体修订已有内容分级与 SEO 质量结论，媒体也有外部预览许可。索引放行受正式环境、显式开关、HTTPS origin、实体质量与内容策略共同约束，未知分类不能直接批量改成允许索引。

缺的是集中运营入口，而不是完全没有 SEO。当前后台“设置”主要管理发现规则，不能当作 SEO 控制台。

依据：[SEO 策略](../../apps/display-web/lib/seo-policy.ts)、[修订编辑](../../apps/ops-web/components/revision-editor.tsx)、[后台导航](../../apps/ops-web/components/admin-shell.tsx)、[既有正式方案](../PRODUCT_SEO_PLAN.md)。

### 建议 SEO 中心 `/seo`（新增）

| 模块 | 管理内容 | 边界 |
| --- | --- | --- |
| 总览 | 可索引实体、禁止原因、待分类、地图候选数、技术异常 | “可索引”不命名为“已被 Google 收录” |
| 页面清单 | URL、标题、描述、canonical、robots、分类、更新时间、地图资格 | 搜索/个人中心等工具页保持既定不索引策略 |
| 内容配置 | 标题/描述模板、必要的单页覆盖、内部链接、图片替代文本 | 复用修订→发布→缓存失效→审计，不绕过发布直接改库 |
| 技术诊断 | 5xx、流式失败、错误 canonical、意外 noindex、死链、地图差异、重复标题 | 区分预期下架 410/缺失 404 与异常，不把全部 404 当故障 |
| 效果 | Search Console 点击、展示、CTR、索引报告；现场性能 | 未连接显示“未连接/无数据”，不是“0 收录/0 流量” |
| 优化任务 | 严重性、规则、URL、证据、责任人、截止日、修复与复测 | 待处理→处理中→待复测→已关闭；复测通过才关闭 |

建议只由 owner 控制生产域名、索引总开关与对外工具连接；内容人员在既有修订权限内维护资料。结构化数据必须与页面可见事实一致，不虚构评分、日期或内容；不对爬虫与用户展示不同的内容分级。

Google Search Console 用于核实抓取/索引问题与搜索效果，需要验证站点所有权；提交 sitemap 有助发现页面，但不保证收录。生产接入需要最终域名和负责人授权，当前可以先开发站内诊断。[官方入门说明](https://developers.google.cn/search/docs/monitor-debug/search-console-start?hl=zh-cn)。

### 优化优先级

- **P0：可访问和暴露风险。** 页面服务错误、流式渲染失败、canonical 指向测试地址、私人页面错误开放索引。最近的“HTTP 200 但页面报错”必须新增正文及浏览器断言，不能只查状态码；部署前验证 `SITE_URL` 与环境组合。
- **P1：索引准确性。** 分类/预览许可未知、标题重复、空资料、地图与页面资格不一致、下架缓存未清、内部断链。优先完善有真实价值的作品/人物/厂牌页面。
- **P2：发现与体验。** 关联内容、内部链接、图片尺寸/压缩/加载方式、移动阅读、广告布局稳定性及真实搜索表现。不以模板化海量建页或关键词堆砌作为增长手段。

测试环境 noindex 不是访问控制。Google 需要抓取页面才能读取 noindex；robots.txt 阻止抓取时，不能依赖它发现页面上的 noindex。建议保护测试入口并保留 noindex 防线；改动公网访问策略需另行确认，避免影响审查访问。[Google noindex 说明](https://developers.google.cn/search/docs/crawling-indexing/block-indexing?hl=zh-cn)。
